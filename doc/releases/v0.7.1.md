# v0.7.1

## What changed

- `lgtm init --agent codex` writes a `.codex/rules/lgtm.rules` that Codex can
  parse. It previously emitted `decision="deny"`, which Codex rejects, and Codex
  discards the entire rules file when any line fails to parse.
- An existing `.codex/rules/lgtm.rules` that lgtm generated is now regenerated
  rather than preserved, so installations carrying the invalid file repair
  themselves on the next init.

## Affected users

This is a correctness fix for Codex users. Nothing else changed.

**Every Codex repository initialized by v0.7.0 has a rules file that enforces
nothing.** Verified against codex-cli 0.146.0, `prefix_rule` accepts exactly
three decisions — `allow`, `prompt`, and `forbidden`. `deny` is not one of them,
and neither are `reject`, `block`, `forbid`, or `ask`. Codex reports the problem
once at session start:

```text
⚠ Error parsing rules; custom rules not applied.: failed to parse rules file
  .codex/rules/lgtm.rules: starlark error: ... error: invalid decision: deny
```

The failure is total rather than partial: one bad line discards the whole file,
so all thirteen default command prefixes were silently inactive while the file
looked installed.

lgtm's own `PreToolUse` hook was unaffected and continued to refuse those
commands, so no repository was left unguarded. What was missing is the
defense-in-depth layer this file exists to provide, which init describes as
present.

Upgrade and re-run init in each Codex repository:

```sh
lgtm update
lgtm init --agent codex
```

Init reports the repair:

```text
note: regenerating ./.codex/rules/lgtm.rules; it was generated by lgtm and is
      replaced rather than preserved
```

The regeneration is scoped by content, not by filename. A file whose first line
is the lgtm generation header is replaced. Anything else is treated as yours and
preserved, as is a file that cannot be read — without its contents there is no
evidence lgtm wrote it, and overwriting your rules is the worse error.

v0.7.0 preserved any existing rules file unconditionally, so no later init would
have repaired one. Without this change the fix alone would have left every
affected installation broken until the file was deleted by hand.

## Upgrade and compatibility

No configuration format changed, and no Claude Code behavior changed.
`.lgtm/execpolicy.json` is untouched — it is the source the rules file compiles
from, and its contents were always valid. Only the generated Codex artifact was
wrong.

## Verification

- `cargo test --locked --all-targets --all-features`: 547 passed, exit 0.
- `cargo clippy --locked --all-targets --all-features -- -D warnings`: exit 0.
- `cargo fmt --check`: exit 0.
- `cargo build --locked --release`: exit 0.
- `lgtm compile --validate`: 71 rules validated, exit 0.
- The accepted decision set was established empirically against codex-cli
  0.146.0 rather than assumed: `allow`, `prompt`, and `forbidden` parse, while
  `deny`, `reject`, `block`, `forbid`, `ask`, `refuse`, `escalate`,
  `deny_always`, `ask_user`, `require_approval`, and `unsafe` all fail with
  `invalid decision`.
- A repository carrying the v0.7.0 file was re-initialized, reported
  `regenerating`, emitted `forbidden` for all thirteen prefixes, and was then
  parsed by Codex with no error.
- Two regression tests: one asserts the emitted decision and rejects the five
  spellings Codex refuses, one covers both directions of the regeneration rule.
- Linux and macOS release builds are provided by the release workflow.
