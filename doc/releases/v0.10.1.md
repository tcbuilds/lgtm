# v0.10.1

LGTM v0.10.1 is the corrected patch release for the v0.10 hardening and observability series. It includes the workspace discovery, enforcement, process-safety, context, and reporting improvements from v0.10.0, plus a release-matrix portability fix for macOS.

## v0.10.0 follow-up

The immutable `v0.10.0` tag did not produce a GitHub release because its Intel macOS release job exposed a same-process `flock` assumption in an integration-test fixture. The production behavior was already covered by the persistent-store tests valid on macOS; the failing fixture specifically assumed Linux same-process lock contention.

This patch gates that fixture on Linux, matching the existing platform-specific lock test and preserving macOS coverage for the locking behavior that applies there. No production code behavior changed in this follow-up.

## Highlights

- Safer nested-workspace discovery with bounded `.gitignore` matching.
- A macOS-compatible release test matrix for persistent-store locking.
- Non-blocking warning feedback for completed `PostToolUse` calls.
- Stronger resource and process containment for self-update, Ruff, and Gitleaks operations.
- More precise path and endpoint signals for policy selection.
- Human-readable coverage evidence in `lgtm report`.

## What changed

### Workspace discovery and `.gitignore` handling

Nested workspace discovery no longer treats `.gitignore` entries as only literal names and suffixes. It now handles the supported forms users commonly rely on:

- Literal and nested path patterns.
- Anchored patterns.
- Wildcard and character-class patterns.
- Directory-only rules.
- Ordered negation rules.
- Trailing `**` patterns.

The matcher is deliberately conservative. Unsupported, malformed, oversized, control-byte, and unrepresentable native-path inputs fail closed rather than exposing a workspace that should have been ignored. Later directory-scoped rules also cannot accidentally erase an independent direct-file ignore.

Discovery traversal is deterministic: filesystem entries are ordered before processing, and marker rescans use the same accounting model. Resource bounds now cover both entries admitted for classification and filesystem entries inspected, including entries that are ultimately ignored. Matching work is charged across pattern parsing, path conversion, wildcard cells, and marker rescans.

The relevant operational limits remain explicit and bounded:

- 64 workspaces per discovery pass.
- 4,096 admitted entries.
- 65,536 filesystem entries inspected.
- 4 MiB of `.gitignore` matching work.
- 4,096 bytes per `.gitignore` pattern.
- 256 KiB of repository metadata.

Symlinks continue to be refused before filtering so an ignored name cannot turn into an escape from the repository boundary.

### PostToolUse enforcement feedback

`PostToolUse` authorization now distinguishes status from severity:

- Failed results with error severity still emit a blocking decision.
- Failed warning- and info-severity results remain in evidence and are reported as review feedback.
- Warning results remain non-blocking and actionable.
- Review feedback is control-character-free and capped at 1,024 Unicode scalar values.
- Remediation text is retained when feedback is truncated.

This keeps hard failures enforceable while allowing lower-severity findings to guide cleanup after a tool has already run.

### Self-update and external-process safety

The self-updater now uses bounded release transfers and safer replacement steps:

- Release archives and checksum files are validated as regular, non-empty files.
- Download output and network operations are bounded.
- Checksums are validated before extraction.
- Updates are staged beside the existing executable, synchronized, and atomically replaced.
- A failed transfer or validation leaves the existing executable in place.
- Temporary update directories are cleaned up after use.
- Supported Unix targets use process-group cleanup for bounded external commands.

Ruff and Gitleaks execution now apply the same containment principles where their process models require them. Gitleaks scans clean up process groups and verify cleanup before classifying results; cleanup or proof failures become unverified instead of being treated as successful scans. Captured output remains bounded, private report directories are removed, and descendants that retain pipes cannot silently outlive the scan boundary.

### Context and policy signals

Context signal consumers now use the same canonical signal vocabulary as their producers. Path matching is component-aware and final-filename-stem-aware instead of relying on broad raw substring matches. This preserves recognized route, API, authentication, Terraform, and workflow observations while rejecting prefix collisions and unrelated path lookalikes.

Endpoint-security activation metadata is aligned with those canonical signals. Selection and explain output now have coverage for route, authentication, and input observations. Prompt-derived signals remain review hints; they are not treated as runtime authorization proof.

### Reports and coverage evidence

`lgtm report` now renders persisted coverage evidence instead of dropping it from the human-readable projection. Coverage output includes its status, workspace, scope, tool identity, line and branch values, and nullable fields where a metric was not available.

Coverage parsing and presentation are bounded and deterministic:

- Schema-closed coverage records are accepted.
- Legacy records remain stable when coverage is absent.
- Hostile Unicode, separators, and malformed values are handled safely.
- Terminal-facing diagnostics are bounded and sanitized.
- External tool paths are reduced to safe basenames.
- Projection ordering is deterministic.
- Optional producer provenance remains available to the evidence model without being copied into the human projection.

## Affected users

All users receive tighter limits and safer failure handling during discovery, self-update, secret scanning, context processing, and reporting.

Projects with nested workspaces may see additional workspaces excluded when their `.gitignore` rules match them. This is intentional: supported ignore rules are now honored, while ambiguous or unsupported rules prefer over-ignore to exposing generated, vendor, or otherwise ignored workspaces.

Users consuming `PostToolUse` feedback will see warning-level findings on stderr as review feedback rather than as blocking decisions. Error-severity findings continue to block. Evidence records retain the original finding status and severity.

Users who inspect reports can now see configured coverage results, including missing or unavailable metrics, instead of having to inspect raw evidence files.

The v0.10.1 follow-up does not change production behavior. It aligns one same-process locking fixture with the platform semantics already used by the implementation and its macOS-valid integration coverage.

## Upgrade and compatibility

No migration is required. Replace the existing binary with the `v0.10.1` build. The `v0.10.0` tag is retained for history but did not publish a GitHub release because its Intel macOS release test failed.

Existing Claude, Codex, and Pi installations, hook envelopes, policy configuration formats, and adapter behavior remain compatible. No new runtime dependency or configuration file is required for this release.

The conservative behavior for unsupported input is intentional: malformed, oversized, unsafe, or unrepresentable data remains fail-closed or unverified rather than being promoted to trusted evidence.

If an existing project depends on a generated or vendor workspace being discovered despite a matching `.gitignore` rule, make that path visible explicitly or adjust the repository’s ignore rules before rerunning discovery.
