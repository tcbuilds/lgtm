# v0.14.0 — 2026-10-19

LGTM v0.14.0 adds two Pi behaviors. Pi can route tools before each model step
and show quiet notices for heuristic findings, through the standalone Jev auto
extension. A new checkpoint extension saves your work before Pi compacts a long
conversation. The release also keeps test installation records out of the real
home registry and repairs process cleanup in test-mode command runs.

This release follows v0.13.1 and includes the changes merged in
[PR #130](https://github.com/tcbuilds/lgtm/pull/130),
[PR #131](https://github.com/tcbuilds/lgtm/pull/131), and
[PR #132](https://github.com/tcbuilds/lgtm/pull/132).

## What changed

### A checkpoint before automatic compaction

Every successful `lgtm init` installs a personal Pi extension at
`~/.pi/agent/extensions/lgtm-checkpoint.ts`. This includes the Claude, Codex,
Pi, global, rules-only, and config migration commands. `--dry-run` reports the
planned install and writes nothing. If the checkpoint cannot be installed, init
reports failure. Files from the earlier init steps stay installed.

Before Pi compacts a long conversation, the extension updates `HANDOFF.md` with
the mission, the observed Git state, and the next actions. It keeps the earlier
handoff in collapsed history. History older than 30 days, or content over the
inline limit, moves to a dated `HANDOFF.YYYY-MM-DD.md` file. Existing archives
are never overwritten. The extension checks an existing plan task only when the
model supplies a matching line and a supporting quote. It never creates a
missing plan.

Limits and safety:

- Manual `/compact` does not write a checkpoint.
- The handoff uses one extra model request on the same provider. It can add cost.
- The extension has a 55-second cancellation deadline, a 45-second model
  timeout, and a 5-second timeout for each fixed Git command.
- A failed checkpoint warns and lets compaction continue. The extension does not
  commit, push, build, or run model-chosen commands.
- The handoff is not a backup and not a security boundary. Do not put secrets in
  conversation text.

Use `/checkpoint-auto on`, `/checkpoint-auto off`, or `/checkpoint-auto status`.
A reload restores the default of on. Remove the file to uninstall it. Another
`lgtm init` installs it again. `lgtm update` does not manage this file yet. See
[the checkpoint guide](../pi-checkpoints.md).

### Jev auto: per-step routing and quiet notices

Jev auto is a standalone personal extension. It is not part of managed LGTM
setup, and `lgtm update` does not install, update, or migrate it. Follow
[the Jev auto guide](../jev-auto.md#install-and-verify-without-a-release) to
install both source files.

Routing runs before each Pi model step through the native `context` event:

- The router sends a short sanitized task, recent tool names, error flags, exit
  codes, and tool names with bounded descriptions. It does not send tool inputs,
  commands, tool output, file contents, or the full conversation.
- It reads the last 32 context messages. It removes credential-shaped text
  before it builds the classifier input. That redaction is a heuristic, not
  proof that arbitrary text has no private data.
- Limits: 256 tools, 8 suggestions, a 0.65 relevance cutoff, 64 attempts per
  session, and a 1-second deadline.
- Pi snapshots the tool loadout before the hook. A newly enabled direct tool
  works on the next model turn, not the request being routed.
- An unchanged sanitized task, recent-result summary, and tool catalog reuse the
  last hint and skip the classifier. Old hints are replaced, not stacked.
- Use `/jev-auto on`, `/jev-auto off`, or `/jev-auto status`. Status shows
  `routed`, `skipped-unchanged`, or `unavailable`.

Quiet notices use a new Pi capability, `lgtm-pi-heuristic-notices` version 1.
A notice is not an approval. Only these findings can enter this channel:

- A complete staged scan with only eligible built-in `generic-api-key` findings,
  after the full deterministic commit gate has run.
- Warning-level review findings from post-tool checks.
- Presentation-only hook diagnostics.

Hard findings, known provider credentials, private keys, custom rules, mixed
findings, prohibited actions, and failed required checks keep their hard
decision. The classifier receives only the notice kind, a safe rule ID, and a
broad path class such as `test` or `source`. No paths, source text, secret
values, candidate hashes, or scanner output go to the classifier.

A noise score of at least 0.90 records the notice silently. Other valid scores
record it and show a nonblocking warning. A missing model, timeout, malformed
answer, busy provider, or spent budget records unknown and warns without a
confirmation dialog. The 0.90 cutoff controls display only. It is an initial
product setting, not a measured accuracy guarantee.

After the notice step, LGTM rechecks the live runtime and reruns one fresh
deterministic assessment. Only the same notice set or a clean result allows the
commit. A new hard finding, changed identity, stale session, cancelled
operation, malformed response, or failed reassessment denies.

Notice limits: 32 notices per event, 16 classified per batch, 20 attempts per
session, 256 remembered identities, and a 1-second deadline. There are no
retries, no persistent answer database, and no extra model turns.

The new extension does not fall back to the legacy confirmation dialog. An old
binary that returns a legacy challenge gets a denial with a refresh instruction.
Older clients keep their v1 behavior. Claude and Codex behavior is unchanged.
See [the Pi adapter guide](../adapters/pi.md#finding-approval-capability) for the
capability contract.

### Test installation records stay out of the real home registry

A test repair stops LGTM's own test runs from writing records into the real
installation registry. The tests now use a test-owned temporary `HOME`.

`lgtm refresh` also reports a project record whose managed root is gone as
stale. It skips that record and keeps it for manual cleanup. A full registry
error and a timeout error are now different messages. The limits are unchanged:
4,096 scanned entries and a 30-second budget. See
[the installation records guide](../adapters/pi.md#user-guide-installation-records-and-test-isolation).

### Containment and coverage

The test-mode command runner now keeps a cleanup reserve inside its deadline.
It can kill, reap, and capture a command that runs too long. A cut-off command
still uses its full share of the deadline. Containment and approval policy do
not change.

CI coverage now measures the standalone Jev TypeScript sources and the
checkpoint integration. This is JavaScript coverage, not whole-Rust coverage.

The real notice-producer integration now runs each scenario in a separate
process and temporary project. Each keeps the existing 60-second JavaScript
watchdog and 75-second Rust supervisor budget. Denial scenarios first prove the
valid notice path works. Failures name the scenario and show its exit status;
production timeouts and security assertions are unchanged.

## Upgrade and rollback

Upgrade with:

```sh
lgtm update
```

Then run `/reload` in each running Pi session, or restart the session. A running
session does not load the new extension until it reloads. Use
`lgtm init --agent pi` once for untracked project hooks. Run that init command
also to install the new checkpoint extension: update alone does not install or
refresh that separate personal extension.

If you use the standalone Jev auto extension, migrate it by hand from a v0.14.0
source checkout. Save the old
`~/.pi/agent/extensions/jev-auto.ts` file outside the extensions directory,
remove that file, create the directory `~/.pi/agent/extensions/jev-auto/`, and
copy `templates/pi/jev-auto.ts` as `index.ts` with
`templates/pi/jev-auto-gates.ts` beside it. Do not keep the old entry point and
the new directory enabled at the same time. The exact steps are in
[the Jev auto guide](../jev-auto.md#install-and-verify-without-a-release).

To roll back to v0.13.1, run:

```sh
lgtm update --version v0.13.1
```

An older binary knows only the hook templates that shipped with it. It may
preserve or refuse a newer generated hook. Before upgrading, keep your own copy
of the managed hook and settings. Restore that matching copy if rollback cannot
refresh the hook. Do not force an overwrite of an unknown extension.

The automatic `lgtm.ts.bak` is created only when absent; an existing canonical
backup is kept and may be older than the hook being replaced. A foreign backup
can block a hook upgrade. Refresh is not one transaction across installations,
so earlier managed files may already have changed when a later step fails.
Reload or restart Pi after restoring a matching setup.

To roll back the checkpoint extension, remove
`~/.pi/agent/extensions/lgtm-checkpoint.ts`, reload Pi, and restore document
contents from Git or the dated handoff archives.

## Verification and limits

The release candidate passed 1,206 tests with an isolated HOME and build
directory. `cargo fmt --check`, strict all-target/all-feature Clippy, and the
locked build passed. The candidate reports `lgtm 0.14.0`. The outer test HOME
contained no installation records after the suite.

An offline upgrade using the published v0.13.1 binary verified project and global
hook refresh with the candidate binary at the same executable path. Both hooks
changed to the new protocol and kept exact initial backups when none existed.

These checks have limits:

- The extension checks use deterministic model stand-ins. They make no paid
  provider call, and they do not certify live provider behavior.
- No paid provider replay and no full native interactive UI conformance run is
  claimed for this release.
- Jev advice is not enforcement. A hard denial from any extension stays a hard
  denial.

See [the Pi adapter guide](../adapters/pi.md) and
[the Jev auto guide](../jev-auto.md) for behavior and limits.
